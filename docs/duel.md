# 双人格对抗：D0–D8

加固阶梯（[`hardening-ladder.md`](hardening-ladder.md)）证明了解码通道能跟上「更复杂的保护」，但它有一个结构性问题：**靶标是固定的**。L0–L5 全部由我自己写，隐藏位置的分布、字面量的形态、没有一条是真正的反制。阶梯本质上是回归测试，不是对抗。

所以再上一层：让两个人格互相追。

- **Defender**（`scripts/duel/defender.mjs`）只做一件事——在**不改变任何字面量**的前提下，把同一份内容藏得更深。它每一代都保留上一代的全部手法，再叠新的，模拟真实目标被分析一次之后加固一次的节奏。
- **Attacker**（`scripts/duel/attacker.mjs`）**只调用插件真正注册的工具**，不碰 `lib/` 里的内部函数。分数反映分析师在报告里看到的东西——包括格式化、截断、排序——而不是某个私有辅助函数恰好能返回什么。

两个人格共享同一份 ground truth（`scripts/duel/truth.mjs`），Defender 用它来藏，Attacker 事后用它来对账。

## 为什么天花板来自 D0

期望列表不能手写。手写的列表会悄悄漂移：改了靶标忘了改期望、或者期望本身写错了，测试就会因为错误的原因通过。

D0 是**全明文**对照组。它跑出来的检出结果——5 个 endpoint、6 条指标文本、15 个追踪维度、8 类反分析标记、1 个水印——自动成为后续所有代际的天花板。之后每一代都拿「和 D0 一样的检出」做分母。

这条规则顺带抓出了三类靶标自身的缺陷：D0 的水印忘了带 `canary=` 前缀导致检测器读不到；D1/D2 漏藏水印；D3/D4 有 `ANTI` 条目没进任何一层。这些都不是检测能力问题，而是**靶标自己没把内容放进去**。现在 `assertCoverage()` 在生成前断言每个字面量都曾被登记，漏一个直接抛错。

## 评分口径

`score = endpoints×0.25 + iocText×0.25 + tracking×0.2 + anti×0.2 + watermarks×0.1`

- **endpoints** 是精确字符串匹配。大小写翻转、截断、多一个尾斜杠都算没检出。
- **tracking / anti** 按**技术族身份**计分，不按证据标记。比如 `debugger| TLS callback` 只有在报告把它归到「调试器」这一类时才得分，光出现「TLS」三个字母不得分。这条规则挡住了「字符串里恰好有 `vm`」这种自欺。
- **watermarks** 单列 0.1，因为它是反追踪的核心指标：能指认「这是哪个分析者的拷贝」比多检出一个 IP 更稀缺。
- **noise** 不计分，但单独报告。它统计的是报告里出现的、不在 ground truth 里的指标条数——一个全靠噪音堆出来的 100% 没有意义。

## 首测暴露的五个真实缺陷

这一轮的修复全部由测量驱动，没有一个来自「读代码觉得应该改」。

| 症状 | 根因 | 修法 |
| --- | --- | --- |
| D2 的 RC4 配置块完全解不出（100% → 15.5%） | 三个判定叠加：`printableWindow` 要求 16/16 全可打印，而长度前缀首 4 字节是二进制 → 真实偏移得 12/16 被拒；可打印比例 0.79 低于 0.82 阈值；64 字节判定窗口在结构化容器里 0.61–0.94 剧烈摆动导致中途截断 | 对齐打分允许 4 字节结构预算并奖励语义锚点；比例阈值降到 0.70；判定窗口扩到 256 字节并允许 2 KB 回溯 |
| D3 解压后追踪只拿到 1/15 | `inflateCandidates` 的 `requireText = true` 拒绝了 `deflate(XOR(records))` 这类二进制输出 | 默认改 `false`：zlib 校验和已经证明流的真实性，不需要再要求文本 |
| D3 的 delta 通道产出 464 条假阳性 | 任何可打印字节的位移段都「像单词」 | 加结构化前置条件（URL / 邮箱 / 注册表 / 路径 / IPv4 / 域名 / 带空格多词），降到个位数 |
| 自定义 base64 解出来全是 shift-1 垃圾 | 错误偏移上仍能产出 200 字节「可打印」输出，`absorb` 判定成功就停了 | `absorb` 改为返回新增数量，只有 `> 0` 才算成功；且压缩帧只走 inflate 分支（压缩字节约 37% 可打印，扫原文必然误判成功） |
| 长 base64 串后半段记录全丢 | 300 字符截断后解码器只看到前几条记录 | 指纹改用长度后缀区分，原串以非枚举 `raw` 属性保留（上限 64 KB），解码器读 `raw` |

## 诚实度：D5 是唯一「该失败」的一代

D5 把一块配置用 `derive(GetVolumeInformationA.serial)` 的结果封存。密钥不在文件里，静态分析**不可能**解开——这是设计目的。

一个只会报「找到了什么」的工具，在 D5 上会和「配置是空的」给出同样的报告。所以评分里加了 `honesty`：**无法解密的区域必须显式上报**，静默是更差的答案。

当前输出：

```
unresolved encrypted region(s): 2 (49152 bytes at .rdata+600, .text+0)
  - no key material recovered, so the key is probably derived at run time;
    plan a dynamic trace instead of assuming the config is empty
```

D5 得分 85%（4/5 endpoint + 全部指标 + 全部追踪/反分析 + 0/1 水印，因为水印就在那块不可解区域里），`honesty = yes`。这个 85% 是**正确行为**，不是缺陷——它准确描述了「静态能拿到什么、拿不到什么、下一步该做什么」。

全程 `honesty failures: none`。

## 真实语料实测

自制靶标有一个天然弱点：我知道检测器会怎么读它。所以对抗跑完后必须回到真实二进制上复核，否则优化的是自己的 fixture。

三件良性样本（`scripts/fetch-corpus.mjs` 下载，跑完即删）：

| 文件 | 大小 | 字符串 | IoC | 追踪等级 | 反分析技术族 |
| --- | --- | --- | --- | --- | --- |
| `7zr.exe` | 602,624 B | 2,405 | 4 | low | 5 |
| `putty.exe` | 1,706,136 B | 4,000（上限） | 41 | medium | 6 |
| `sqlite3.dll` | 3,181,056 B | 4,000（上限） | 1 | low | 5 |

0 错误、0 崩溃；良性软件没有出现 `high`/`critical` 追踪误报（putty 的 `medium` 来自 SSH 协议字符串，合理）；没有未解区误报。

**这一轮最重要的数字是 IoC 从 22 掉到 4。** 7zr 原来报的 22 条里有 18 条是这种：

```
email O@..OV..OG      email KOZGA@..mO      domain qMTXXZ.cN
email G@I...mAC       email GGGFG@GG.HPd     domain gXZ.cN
```

全部来自「255 个密钥全扫」的乱码解码。对分析师来说，混进报告的假指标比漏一个真指标更糟——它会让整份报告失去可信度。清掉之后剩下的 4 条（`schemas.microsoft.com`、`1.0.0.0`、`3.3.33.5`、一条 MS 命名空间 URL）都是真的。

## 单字节 XOR 的密钥筛选：两次都错，第三次才对

这一段单独记下来，因为它是「凭直觉优化」连续失败两次的完整案例。

**问题**：255 个密钥 × 512 KB 字符串构建，7zr 上要 9.4 秒。

**第一次尝试**：按 run 形状 triage——要求可打印 run ≥ 8 且值至少变化 4 次，只对最「高产」的前 48 个密钥做全扫。

失败。7zr 是文本密集的 C++ 程序，ASCII 段在**所有** 255 个密钥下都能产生长 run（存活 255/255），triage 完全没有区分度。更糟的是它挑错了：`0x21..0x3f` 里的密钥把整块明文映射到另一个可打印区间，以 319 字节的 run 夺冠；而真正用到的密钥只排到 153 字节、第 70 名，被 48 的截断直接扔掉。

这个 bug 让 L1 的 hidden 召回从 3/3 掉到 1/3，是靠 `git archive HEAD` 跑同一批样本才定位到「是回归，不是我多疑」。

**第二次尝试**：换成「哪个密钥**可证明**能解出语义锚点」。探针 P 在偏移 i 出现，当且仅当 `k = window[i] ^ P[0]` 且后续字节在同一個 k 下一致——所以每个探针一遍线性扫描就能得到值得全扫的密钥集合，不需要猜 run 长度，也不需要拍脑袋的密钥上限。

**但探针长度必须 ≥ 4**。从首字节推密钥不花任何代价，所以长度 L 的探针只约束 L-1 个字节，每 `256^(L-1)` 个偏移就会凭空造出一个假密钥。512 KB 窗口下：`'.io'` 造 8 个，裸的 `':\\'` 造出上百个。这些假密钥每个都要一次全扫，反而把真密钥淹没。4 个字符把期望值压到 0.03。

同样的问题出现在 IPv4 上：纯数字没有字母，任何文本探针都够不到它，而 C2 地址恰恰是最不能丢的 IoC。解法是利用「密钥在相邻字节的 XOR 差里抵消」这一点，锚定某个 `.` 后把整段 `d.d.d.d` 走一遍、第一个不匹配就退出。两三个宽松的数字判断不够——每个只能排除 8/256 的偏移空间，仍会造出几十个假密钥。

**最终数字**：

| 文件 | 1.6.0（255 密钥全扫） | 1.7.0（锚点探针） |
| --- | --- | --- |
| `7zr.exe` | 2,068 ms | 513 ms |
| `putty.exe` | 182 ms | 401 ms |
| `sqlite3.dll` | 140 ms | 257 ms |

7zr 快 4 倍，另两个慢约 2 倍——因为探针要对 50 多个锚点各扫一遍窗口，而旧 triage 只扫一遍。这是**故意的交换**：换掉的是一个会在真实目标上静默丢密钥、并在良性文件上产出 18 条垃圾 IoC 的启发式。

顺带一个纯工程优化：探针内层里每个偏移查一次 `Set`，50 多个探针 × 512 K 偏移 = 2800 万次哈希，比它要保护的正经工作还贵。换成 256 位图后 7zr 从 900 ms 降到 513 ms。


## 1.8.2：第一个由引擎判分的维度

前面的维度全部由本地静态层打分，因此再严格也只在「假设」内部自洽。装上 Ghidra 12.1.4 之后，报告多输出一行机器可读的探针（`probe: inspect_address_context @ 0x409800`），攻击方读它、真的调用 REA、把返回的符号名当分数。D6–D8 都解析出 `tls_callback_0`；D8 的盐仍然拿不到——`verify` 证明的是「这条实验跑得通」，不是「样本被解开了」，两者不能混算。

同一次实测打回了四处缺陷，其中三处是「文档说得对、工具做不到」：

- `batch_decompile` 指向 TLS 回调必然失败：回调由数据指针引用，Ghidra 不建函数，返回 `invalid_request: No procedure exists at 0x409800`。计划里改成 `inspect_address_context` 才跑得通。
- 报告只给 RVA 不给镜像基址，读者无法把 RVA 变成引擎要的 VA。
- 侧栏把 JDK 17 报成 ready，而 Ghidra 12 只认 21+，实际问题被藏在一个「ok」后面。
- 侧栏保存的 `JAVA_HOME` 被子进程继承值覆盖，配置形同虚设。

安装位置：`<repo>/.tools/`（`ghidra_12.1.4_PUBLIC` + `jdk-21.0.13+9`），C 盘只留 `rea-engines/config.json` 里的两个路径字符串。若宿主限制子进程只能写工作区，`TMP`/`TEMP`/`APPDATA` 必须一并指过去，否则 REA 的私有运行目录会让 JVM 在写 `java_home.save` 时被拒，Ghidra 会误报「找不到 JDK」。

## 1.8.7：不再问 REA 要引擎

1.8.6 的判断是「第五道门堵不上」。门确实堵不上——但那道门只属于 REA 的那条路。`analyzeHeadless.bat` 一直在安装目录里，谁调用它，项目目录就由谁决定。

### 五个门，一个都不需要绕

| 门 | REA 路径 | 本插件自己启动 |
| --- | --- | --- |
| tmp / cache / config | 私有运行时内，JVM 不可写 | `_JAVA_OPTIONS` 指到自有目录 |
| ghidra.log | `-log` 由 REA 固定 | 换成无 include 的 log4j 配置，只写 stderr |
| 项目目录 | `-projectPath` 由 REA 指定 | 由本插件指定 |

三个真实障碍，都与权限无关：

1. Ghidra 拒绝任何以 `.` 开头的路径元素，`~/.dsh/**` 一律不可用；
2. 安装路径含非 ASCII 时，`generic.log4j.xml` 的相对 include 经 `jar:file:` 百分号编码后失败，启动中止；
3. `-process` 接的是可选**程序**名，传项目名会让 Ghidra 找不到程序而中止。

### 结果

| 代际 | verify（1.8.6 → 1.8.7） | score |
| --- | --- | --- |
| D6 | local → **引擎档，`tls_callback_0`** | 89.0% → 100% |
| D7 / D8 | local → **引擎档** | 100% |
| D9 | local → **引擎档** | 92.8% → 100% |

规划器现在**优先**用自己的引擎：被包裹 provider 的「就绪」是对看不见的沙箱的猜测，第一次调用才是验证；1.8.6 的 D6 就死在那次验证上。

### D10：齐全的导入表

十代满分说明阶梯失去区分度，所以 D10 换个方向——26 个真实但从不调用的导出，紧挨着 ROR13 真表。工具里那行 `if (named >= 24) return imports;` 让它在 D10 上拿到 **api 1/9、behaviour 4/6、84.4%**。

修法不是调阈值，是承认那句话不成立：目录被填满是「名字被写过」，不是「名字被写全了」。现在无论多满都扫哈希表，`namedCount` / `hashedCount` 分开上报，`overlappingSources` 标出冲突，规划里多一步「决定 loader 走哪一套」。

### 评分：fabricated 与 ambiguous

D9 的 22 条噪声 = 8 条良性 + 12 条自己种的诱饵 + 2 条从诱饵派生的 host。工具一条都没编造，旧算法却按 42.1% 扣分。

现在防守方用 `bait:` 声明种下的值（与 `seal()` 同一套自证逻辑），评分分开：

| 代际 | noise | ambiguous | fabricated | precision |
| --- | --- | --- | --- | --- |
| D9 | 22 | 12 | 10 | 100% |
| D10 | 7 | 0 | 7 | 100% |

### 饱和

十一代全部 100%。这不是「完美」，是**这批代际已经测不出东西了**；「weakest D1」只是并列排序的产物。下一步要么换样本轴（真实加壳、Go/Rust 产物），要么覆盖动态路径（Frida 至今零覆盖）——继续加 D11 同类变形只会继续满分。

## 1.8.6：verify 不再依赖引擎

1.8.5 收尾时列了一个「还剩」的缺口：Ghidra 的 `ghidra.log` 写不进 REA 的私有运行目录。这一轮把它堵上了，然后撞上第五道门。

### 前四道门能挪，第五道不能

| # | 需要的位置 | 能否绕过 |
| --- | --- | --- |
| 1 | `tmp/<user>-ghidra` | `-Dapplication.tempdir` |
| 2 | `cache/<user>-ghidra` | `-Dapplication.cachedir` |
| 3 | `config/<user>-ghidra/<release>` | `-Dapplication.settingsdir` |
| 4 | `<root>/ghidra.log` / `script.log` | `-Dlog4j.configurationFile` 指向不写文件的配置 |
| 5 | `<projectPath>/*.gpr`、`.rep` | **不能**：参数由 REA 传，路径在私有运行时里 |

前四道逐个验证过，错误确实依次推进（temp → cache → config → log → project）。第五道停在 `DefaultProjectData.init` 的 `createNewFile`：Ghidra 必须在项目目录里建数据库，而这个目录的 DACL 只允许 REA 自己的原生进程写入。

### 于是让 verify 不需要引擎

新增 `lib/probe.js` 和自有工具 `rea_probe_address`。判据是文件本身：

- `kind: code` → 该 RVA 必须落在可执行节（TLS 回调就是这一类）；
- `kind: pointer` → 该 RVA 处的 dword 必须指向可执行节（派发表条目）。

规划器在引擎不可用时把同一个地址改派给本地探针，并保留 `blocked` 原因：

```
probe: inspect_address_context @ 0x409800 (code)          ← 引擎可用
probe: probe_address @ 0x409800 (code) [local structural check]   ← 引擎不可用
```

### 评分：两档，都要求真的对上

| tier | 判据 | 说明 |
| --- | --- | --- |
| `engine` | `ok` 且解析出符号名 | 名字才是引擎相对「读文件」多出来的东西 |
| `local` | `verdict: code` / `pointer` | 不能命名，只证明结构符合断言 |

| 代际 | verify | score |
| --- | --- | --- |
| D6 | NO（engine，失败） | 89.0% |
| D7 / D8 | local | 100% |
| D9 | local | 92.8% |

十代均值 97.9% → **98.0%**。分数几乎没动，但**维度从「不可测」变回「可测」**：D7/D8 的地址被真的读了一遍，而不是因为引擎缺失就跳过。

本地档不是白送：把 `.rdata` 的派发表地址当 `code` 探，`verdict: not-executable`，记 0；把普通 dword 当 `pointer` 探，`not-a-code-pointer`，记 0。`test/probe.test.js` 固定了这两种失败。

## 1.8.5：把「不可达」拆成「没试到」

1.8.4 的结论写得很干脆：D8 的盐被密封，9 个 API 名静态不可恢复，`api 1/9` 是真实能力缺口。这一轮推翻了它。

### 手工三分钟，工具三个月

D8 的配置在 `cfg=deflate+xor;key=2b8d41f0;` 后面。手工解：

```
header → key = 2b8d41f0
inflate(payload) → 709 bytes
xor(result, key) → /https://telemetry...   FirebaseAnalytics   ... salt=0x5d3a91c7
```

工具前两步都做了（`inflateCandidates` 找得到 `at 820, zlib, 709 bytes`），第三步没做：

- XOR 阶梯只在第 1 层（`depth === 0`）跑；
- 嵌套层只跑 `inflateCandidates` 和单字节 XOR 的语义锚点判定，不会拿 4 字节重复键去试；
- 而 key 就写在 header 里，明明白白。

### 修法：让 header 从注释变成指令

| 层 | 改动 |
| --- | --- |
| 字符串 | 容器阶段读 `cfg=…xor…;key=<hex>;`，用声明的 key 解 inflate 结果后递归挖（hex 2–8 字节、前 4 KiB） |
| 哈希 | `buildHashIndex({ salt })` 为每个字典名加一条 `hash ^ salt`，算法标 `+salt` |
| 结构 | `structureProfile(bytes, { salt })`，`hashedApis.salt` 随结果上报 |
| 编排 | triage 先解字符串、取 `salt=0x…`，再解析导入与结构；`cfg=`/`salt=` 行钉在隐藏字符串列表头部 |
| 文案 | `mul31-xor-2f with salt 0x5d3a91c7`，不再把 `+salt` 当算法名 |

### 结果

| 代际 | api | behav | score（1.8.4 → 1.8.5） |
| --- | --- | --- | --- |
| D8 | 1/9 → **9/9** | 4/6 → **6/6** | 82.5% → **100%** |
| D6 | 9/9 | 6/6 | 89.0%（不变，唯一 verify 假声明） |
| D9 | 9/9 | 6/6 | 91.9%（不变，precision 42.1%） |

十代均值 95.9% → **97.9%**，weakest 从 D8 变成 D6。

### 引擎：四个缺口，三个能绕

`verify` 长期 `n/a` 的根因也查到了底。Ghidra 在 REA 的私有运行目录里依次要：

1. `tmp/<user>-ghidra` —— 可用 `-Dapplication.tempdir` 绕；
2. `cache/<user>-ghidra` —— 可用 `-Dapplication.cachedir` 绕；
3. `config/<user>-ghidra/<release>` —— 可用 `-Dapplication.settingsdir` 绕（但 REA 预创建的是 `config/ghidra`，路径假设本身不对）；
4. `<root>/ghidra.log` —— **绕不过**：REA 用 `-log` 把它交给 analyzeHeadless，Ghidra 据此 `setApplicationLogFile`，覆盖任何 `-DlogFilename`。

我逐个验证过前三个（错误确实依次推进），第四个卡在 `Null object returned for RollingFile`。REA 又会清空 `JAVA_TOOL_OPTIONS`/`_JAVA_OPTIONS`/`JDK_JAVA_OPTIONS`，所以不改打包产物就进不去。验证完把引擎配置原样恢复，`classifyEngineFailure` 改成按目录分类上报。

### 边界

- 只有**样本自己声明** key / salt 时这条链才成立。没声明的盐仍不可达。
- `verify` 继续 `n/a`。

## 1.8.4：第十个维度，和一代专门说假话的样本

1.8.3 末尾留了一个待办：九维评分只罚漏报。D2 多报两条噪声、D9 把十几个诱饵当事实，分数都不动。这一轮补上精确率，并造了 D9 去证明它真的能抓到。

### precision 的算法与自证方式

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 基线 | 控制代 D0 的噪声数（8） | 明文无保护样本上的噪声就是工具的「良性闲聊」，不是手写期望 |
| 容差 | 3 | 控制代自身波动；解码通道会合理多出 1–2 条（URL→host、email→domain） |
| 尺度 | 8 | 每多 8 条额外候选，precision 减半 |
| 权重 | 0.12，其余九维 ×0.88 | 零额外噪声的代际分数不变，不重写历史序列 |

评分规则从 `scripts/duel.mjs` 抽到 `scripts/duel/score.mjs`，11 个单测固定住：权重和为 1、满分行不受新维度影响、sealed 从可达集合移除、全封维度记 `null`、`null` 维度重分配而不是记 0。

### D9：可恢复，但假货比真货多

D8 的边界是「信息不可达」；D9 换一条轴——**全部可达，但判断力被攻击**：

- 12 条明文诱饵 IoC（3 URL / 3 email / 3 IP / 3 域名），格式合法，全部不在真值集；
- 第二张哈希表：CRC32 算的 10 个「字典里有、样本从不调用」的 API，紧挨着 D6 的 ROR13 真表；
- 结构沿用 D6（TLS 回调、24 项派发表、无导入目录），所以召回侧没有借口。

| 指标 | D6（无诱饵） | D9（有诱饵） |
| --- | --- | --- |
| endpoint / indicator | 4/4 · 5/5 | 4/4 · 5/5 |
| api / behaviour | 9/9 · 6/6 | 9/9 · 6/6 |
| 噪声 | 7 | 22 |
| precision | 100% | **42.1%** |
| 总分 | 89.0%（verify 一次假声明） | 91.9% |

同样一份报告，九维评分会给 D9 100%。它现在拿 91.9%，差的 8.1% 全在判断力上。

### D9 打回的三处缺陷

1. **「confirmed」是反的**。`url (3 confirmed, 4 recovered)`：3 条 confirmed 全是明文诱饵，4 条真正从配置解码出来的反而是 recovered。工具把「容易被看见」当成了「可信」。现在叫 `observed in plaintext` / `decoded`，每条明文挂 `— unverified`，并在报告里写明清白：静态提取分不清活跃 C2、投放诱饵与死字符串。
2. **随机字节被当成 email**。`J@nC.NDH`、`ID@qo.HIplXO`、`bido@ihl.xml` 代代出现。email 规则加 TLD 白名单、域名段必须小写后全部消失，真实地址一条没少。
3. **混合算法被描述成一个算法**。`19 names matched, and ror13 fits those`——19 个名字横跨 ror13 与 crc32。现在按算法分组，并明确「至少一组是诱饵」，`structure:` 行也补了 `mixed algorithms: likely separate or decoy tables, names unverified`。

### 一个必须说清的局限

D9（91.9%）高于 D8（82.5%）。这不是 bug：D8 缺的是能力（api+behaviour 合计 0.28），D9 缺的是判断力（0.12）。加权总分会把两者混成一个数，所以 `precision floor` 单列在报告里——「满嘴胡话但全都提到」不该因为总分更高而看起来更好。

### 未解决的

- D8 的盐仍不可达，`api 1/9` 是真实能力缺口；
- API 诱饵没有并入加权分数（D0 导入表与哈希代际没有同源基线），改由报告诚实度与回归测试覆盖；
- `verify` 继续 `n/a`：REA 会清空所有 JVM 注入变量，不改第三方产物就塞不进 `-Dapplication.tempdir`。

## 1.8.3：评分先自证，再谈能力

1.8.2 的 `verify` 在这一轮直接失效：所有代的探针全部 FAILED，`verify` 记 0，均值从 94.5% 掉到 90.0%。原因不是分析能力退化，而是**引擎在这台机器上根本起不来**：Ghidra 的 JVM 无法在 REA 的私有运行目录里创建 `<user>-ghidra` 临时目录。用 REA 自带的 `rea decompile` 复现同样失败，确认是上游 Windows 限制，与本插件的集成无关。

修补上游要改三份打包产物、升级即失效，所以改的是断言本身：

- 新增引擎健康账本：工具层从错误信封取 `provider_id`，把失败压成一行原因并记账；`providerReadiness()` 合并账本，失败过的 provider 在本次会话里不再声称就绪。
- 修掉「探针活过引擎死亡」：`inspect_address_context` 没进 `PROVIDER_OF_CONFIRM`，TLS/派发表步骤从来没被打上 provider 标签。补上之后，provider 不就绪时规划器会删掉 `probe:` 行并写入 `blocked`。
- 一次会话内的行为因此是**自适应**的：D6 在账本还空时断言「就绪」→ 引擎死 → 扣掉 `verify`（87.5%）；D7/D8 已经不再声称，探针撤下，维度转 `null` 而不是记 0。

同一轮里还有一处评分自证问题。D5–D8 把 `device/register` 和唯一水印封进「运行时派生密钥」的容器，`honesty` 维度为「有没有承认打不开」计分——但同一批字面量又被 `recall` 扣了一遍。一处不可能，罚两遍，任何分析员都拿不到那 4–8%。

现在防守方用 `seal()` 声明封存值，评分按「该代际真正可达的天花板」计算：

| 机制 | 作用 |
| --- | --- |
| `seal()` | 同时写入 `tracked` 与 `sealed`，`assertCoverage` 校验「声明封存的必须真被编码过」 |
| 可达集合 | D0 天花板 − 封存值；`endpoints` 从 5 变 4、`iocText` 从 6 变 5 |
| 全封维度 | 水印被封完时记 `null`，权重重新分配，不白送 0 |

结果：九代均值 **95.9%**（D0–D5、D7 100%，D6 87.5%，D8 79.6%），honesty failures 0。D8 的 `api 1/9` 保留——盐确实不可恢复，但那是**能力缺口**，不是不可测：报告应当说「哈希表存在、算法未知」，而不是假装认得。

## 1.8.0：从「字符串在不在」到「分析师该回答什么」

1.7.0 的五个维度全是字符串召回。它能测出「勘查员」的水平，测不出「独立分析师」——后者还要回答结构、行为，以及「下一步做什么实验」。

### 三个新维度

| 维度 | 问的问题 | 怎么算分 |
| --- | --- | --- |
| `api` | 导入表被抽掉后，还能不能叫出 API 名字 | D0 导入表里的 7 个高信号 API，在报告里出现几个 |
| `behavior` | 能不能说出「它在干什么」 | 6 类行为（设备标识 / 外联 / 持久化 / 反调试 / 注入 / 加密）覆盖几类 |
| `plan` | 能不能给出「下一步做什么实验」 | 有封存区时，实验须点名 hook API 与动作；没有封存区则该维度不计分，权重重分配 |

权重从 `0.25/0.25/0.2/0.2/0.1` 调成 `0.15/0.15/0.10/0.12/0.05` + `api 0.15 / behavior 0.15 / plan 0.13`。字符串仍是大头，但「说不清结构」不再能用字符串刷分掩盖。

### 三代新靶标

| 代际 | 加了什么 | 首测 | 现在 |
| --- | --- | --- | --- |
| D6 | 抽掉导入目录 + ROR13 哈希表 + TLS 回调 + 24 项调度表 | 92% | 92% |
| D7 | 哈希换成私有乘法族（`imul 0x1f` / `xor` / seed `0x2f`） | **72%** | **92%** |
| D8 | 哈希加盐，盐封在不可解区 | **72%** | **72%** |

**D6 的 92% 不能算盲测通过**：结构模块是先写的，靶标是照着它写的。这是这轮的方法论弱点，写在这里而不是藏起来。D7 才是干净的对照：先测出 `api 0/7`、`behavior 4/6`（72%），再把五个固定算法扩成「乘数 × 运算 × 种子」的参数族，复测 `7/7`（92%）。

D8 是新的边界：哈希循环本身普通，但盐每次构建不同、只存在于封存配置里。任何算法族都对不上，正确答案是「10 个哈希项，算法未知，盐可能被封存」——报告必须这么说，不能猜。

### 本地层与 REA 的分工

这轮新增的 `lib/structure.js` 与 `lib/plan.js` 都在本地跑，不调用任何引擎。原因不是「REA 做不到」，而是**顺序**：triage 要在没有引擎、没有打开目标、甚至没装 Java 的机器上，先回答「值不值得送进反编译器」。

但本地层只能出假设。所以每个实验步骤都带 `confirm` 字段，点名用哪个 REA 工具证实：封存区用 `load_frida_script`，TLS 回调用 `batch_decompile`，调度表用 `execute_rizin_command`。报告里也明确写「这些是静态假设，不是发现」。

这条边界也修了一次真实重复：`lib/structure.js` 初版自己抄了一份 API 字典与五个哈希函数，而 `lib/api-hash.js` 早就有。现在结构模块只消费它的结果——同一份算法只应存在一处。

### 合成靶标测不出的三件事：真实语料打回

八代靶标全过之后，用 1.8.0 扫了三份真实二进制（7zr.exe / PuTTY / sqlite3.dll，共 5.5 MB，`npm run fetch-corpus && npm run corpus-scan`）。结构层当场出错，而且错法是「听起来很专业」的那种：

| 缺陷 | 真实表现 | 修法 |
| --- | --- | --- |
| switch 跳转表被当成控制流平坦化 | 7zr.exe 报出 **33 张调度表**——全部是 MSVC 为 switch 语句生成的跳转表。`plan` 的第一条建议因此指向其中一张：「记录 RVA 0x7c2e0 处间接跳转的索引，索引序列能还原真实块顺序」 | 先数数量：代码指针表 > 3 张时只登记、不指控（这个数量本身就是 switch 表的特征）；≤ 3 张才作为候选，且每条都标 `confidence: 'low'`，`why` 写明「switch 表形状完全相同，只有解码循环能区分」 |
| 未初始化数据被当成结构异常 | `.data` 虚拟大小是原始大小的 31.2 倍 → 报异常。这是 BSS，每个 C 程序都有 | 只对**可执行节**膨胀报异常（自解压 stub 才会这样） |
| 报告自相矛盾 | `behavior.summary` 写「无法从静态证据归因」，`families` 却列了 `T1082/T1140/T1537` | `families` 改为从 findings 推导，ATT&CK 能力提示留在自己的字段里 |

为什么靶标测不出来：Defender 造的 PE 里只有一张表，因为「一张表」正是它希望你发现的东西。真实软件里表是按编译器习惯成批出现的——33 张表里没有一张是调度器，这个判断不依赖任何解码，只需要数数。

修完后的真实输出：

| 样本 | 代码指针表 | 指控平坦化 | 结构异常 | 行为 findings |
| --- | --- | --- | --- | --- |
| 7zr.exe | 28 | 否（并说明原因） | 0 | 0 |
| putty.exe | 0 | 否 | 0 | 4（全部 `import-table`，`low`/`medium`，附证据名） |
| sqlite3.dll | 0 | 否 | 0 | 1（`anti-debug`，证据 `isdebuggerpresent`） |

PuTTY 的 4 条是「能做」而不是「在做」：写注册表配置（`RegSetValueExA`/`RegCreateKeyExA`）、读用户名（`GetUserNameA`）、查调试器（`IsDebuggerPresent`）、碰剪贴板（`OpenClipboard`/`GetClipboardData`）。对一个 SSH 客户端来说四条全是真的，所以措辞必须是能力而非结论——这正是 `source` 与 `confidence` 两个字段存在的理由。

## 边界（明确写下来，不假装没有）

- **运行时派生密钥**：D5 那块配置静态无解。工具会说要动态跟踪，不会假装配置是空的。
- **诱饵块会被报成未解区**：D4 的 24 个高熵 decoy 在静态上和真密文完全无法区分，所以报告里会出现「有区域打不开」。这是诚实默认值，不是误报——但分析师看到 49 KB 的未解区时应该先怀疑诱饵。
- **单字节 XOR 探针只认锚点**：如果一个 XOR 字符串既不含 URL/域名/注册表/路径/邮箱，也不含任何已知追踪关键词，它不会被这条通道拿到。`delta`、`crib dragging`、`blobs` 三条通道从另一侧覆盖同一片地面，但没有哪条是全覆盖的。
- **三字符 TLD 缺探针**：`.io` / `.ru` / `.cn` 单独作为探针会造假密钥，所以被移出列表。裸域名以这三个 TLD 结尾、且字符串里不含 `http`/`www.` 的 XOR 块会漏。
- **确认路径可能整条不可用**：1.8.0 的实验都点名了 REA 工具，但本机六个 provider 全缺（Ghidra/JADX/objdump/rizin/gdb/frida），任何 `confirm` 都执行不了。1.8.1 起报告逐条标 `[frida: unavailable - frida not on PATH]`，并在顶部给 `engines: 0/6`。假设层与确认层之间的缝，必须写在报告里而不是留在读者的推断里。
- **switch 表与调度表无法离线区分**：两者的静态形状完全一样（只读区里的代码指针连片 + 单一间接跳转）。数量门槛能把「编译器习惯」挡掉，但一个只用一张 switch 表的正常函数、和一个只用一张表的平坦化函数，静态上没有区别——只能交给 `execute_rizin_command` 看解码循环。

```bash
npm run duel                      # 生成 D0–D8，跑攻击，出 dist/duel/duel.json
npm run duel -- --out /tmp/x      # 换输出目录
npm run ladder                    # 1.6.0 加固阶梯（D0 之前的那一层）

```

`scripts/fetch-corpus.mjs` 下载的三件良性样本只用于复核，跑完用 `--clean` 删除——它们不进仓库、不进发布包。
